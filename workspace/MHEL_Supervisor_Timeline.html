The project moved through four stages over the semester: implementing and stress-testing two established retrieval baselines (MVD, BLINK), evaluating a stronger multilingual baseline (mReFinED) and carrying its most reliable components forward, and finally building our own system, MHEL-LLaMo, on top of that foundation with an original confidence-routing contribution.

1

Stage One

MVD — first baseline, on constrained hardware

We began with MVD, a multi-view dense-retrieval distillation approach, to establish a first working retrieval baseline. The published setup assumes four dedicated high-memory GPUs; our available hardware was a shared four-GPU cluster with less memory per card and other jobs competing for the same resources.

  • Built a GPU-availability check so evaluation runs automatically avoided GPUs already in use by other jobs on the shared server.
  • When a full run was interrupted partway through by memory pressure, we implemented a checkpoint-resume strategy — restarting only the remaining stages at a reduced batch size instead of re-running everything from scratch.
Achievement

Got MVD training and evaluation running end-to-end on shared, lower-spec hardware than the paper assumes, without needing dedicated infrastructure — establishing our first working retrieval baseline and a resume-safe evaluation workflow we reused later.

2

Stage Two

BLINK — second baseline, across seven datasets

We next implemented BLINK as a second, independent baseline, targeting seven standard entity-linking benchmarks. BLINK's full model set — bi-encoder, cross-encoder, entity catalogue and entity encodings — is large, and its original codebase predates our current software stack, so getting it running took real integration work.

  • Resolved missing dependencies and rebuilt incomplete benchmark data files before evaluation could run at all.
  • Pinned specific library versions to bridge BLINK's older codebase onto our modern CUDA/PyTorch environment.
  • Managed the transfer and staging of a large multi-part model set across machines, with disk-space cleanup built into the evaluation scripts so repeated runs didn't fill available storage.
Achievement

Reproduced BLINK end-to-end across all seven benchmark datasets, matching published bi-encoder and cross-encoder numbers (e.g. AIDA-testb, MSNBC, ACE2004) and giving us a second, independently validated baseline to compare against.

3

Stage Three

mReFinED — validating the foundation before building our own system

Before committing to a final architecture, we thoroughly evaluated mReFinED, a stronger and more recent multilingual entity-linking framework, across nine languages on Mewsli-9 and four languages on TR2016. This stage was deliberately treated as due diligence — we wanted to know exactly how well an established multilingual system performed, and why, before deciding what to build on top of it.

  • Diagnosed and fixed a GPU memory-fragmentation issue that was silently limiting utilisation to 20–30% instead of the expected 80–90%, by correcting how the (very large, ~33GB) model was placed on the device.
  • On TR2016, traced a low initial score back to a genuine data-quality defect — 40–55% of the gold-standard mention positions in the source data were corrupted — rather than accepting it as a modelling failure. Built an offset-validation fix that more than quintupled recall on the affected language.
  • Identified which parts of mReFinED were reliable and reusable: its multilingual candidate-generation lookup, its evaluation harness, and its dataset-conversion pipeline.

Achievement

Rather than treating mReFinED as just another number on a table, we used this stage to validate and carry forward its strongest components — its multilingual candidate lookup and evaluation pipeline — into our own system, and caught a real data-integrity bug along the way that a less careful reproduction would have missed.

4

Stage Four — Final System

MHEL-LLaMo — our own system, built on that foundation

With the baseline work and the validated mReFinED components in hand, we built MHEL-LLaMo: a multilingual bi-encoder retrieves candidate entities for each mention, and a confidence signal decides whether a mention can be resolved directly or needs to be escalated to a large language model for harder cases. On top of the reproduced pipeline, we added our own original contribution and adapted it to run within our hardware budget.

  • Our own contribution: a machine-learned confidence router (XGBoost) that decides, per mention, whether to trust the retrieval result directly or escalate to the LLM — trained on over 22,000 labelled examples.
  • Hardware engineering: the language model we use is large enough that running it at full precision would need roughly 96GB of GPU memory; our available GPUs have 24–32GB. We closed that gap using mixed-precision computation together with gradient accumulation, bringing the working footprint down to about 28GB with no loss in output quality.
  • Validation: reproduced the published results on all four target benchmarks, then measured our router's improvement on top of that reproduction.

Where this leaves us

Across the semester we went from standing up two independent published baselines on constrained shared hardware, to thoroughly validating a stronger multilingual framework and deliberately carrying its best components forward, to a final system that reproduces published results exactly and then improves on them with our own confidence-routing method — all adapted to fit within the GPU budget we actually had.

Next planned steps: completing evaluation of a retrieval-reranking extension currently staged for two of the benchmark datasets, and finishing evaluation on one additional historical dataset that required extensive data-recovery work before it could be used at all.
