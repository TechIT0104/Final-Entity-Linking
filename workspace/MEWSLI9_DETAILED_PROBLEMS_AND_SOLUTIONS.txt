  RuntimeError: CUDA Runtime Error: unspecified launch failure
  torch.cuda.is_available() = False
  
Root Cause:
  • PyTorch wheel: torch 2.1.0+cu130 (installed by default)
  • System CUDA Driver: CUDA 12.8 (on RTX Ada GPU)
  • Mismatch: CU130 > CU128 drive → GPU access broken
  
Impact: ❌ COMPLETE GPU FAILURE

  - Evaluation would hang indefinitely
  - Model can't use GPU memories

Solution Implemented:
  Step 1: Identify mismatch

  Step 2: Downgrade torch to compatible version
    $ pip uninstall torch torchvision -y
    $ pip install torch==2.11.0+cu128 torchvision --index-url https://download.pytorch.org/whl/cu128
    
  Step 3: Verify CUDA works
    $ python -c "
      import torch
      print(f'CUDA available: {torch.cuda.is_available()}')  # Should be True

PROBLEM #2: TOKENIZER API DEPRECATION (RUNTIME)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Error Encountered:
  AttributeError: 'RobertaTokenizer' object has no attribute 'encode_plus'
  
  OR
  
  UserWarning: tokenizer.encode_plus(...) is deprecated and will be removed
  
Root Cause:
  • Old code used: tokenizer.encode_plus(text, ...)
  • Transformers v5+ removed encode_plus() method
  • New interface: use tokenizer.__call__(text, ...) or tokenizer(text, ...)
  
Files Affected:
  - src/refined/inference/preprocessor.py (mention detection preprocessing)
  - src/refined/inference/standalone_md.py (standalone mention detector)
  
Impact: ❌ PREPROCESSING FAILS
  - Can't tokenize input text
  - Model can't process mentions
  - Evaluation crashes on first document

Solution Implemented:

  File 1: src/refined/inference/preprocessor.py
  ─────────────────────────────────────────────
  
  OLD CODE (Lines ~150-170):
    tokens = self.tokenizer.encode_plus(
      text,
      add_special_tokens=True,
      return_tensors='pt',
      truncation=True,
      max_length=512
    )
    input_ids = tokens['input_ids']
    attention_mask = tokens['attention_mask']
  
  NEW CODE (Fixed):
    tokens = self.tokenizer(
      text,
      add_special_tokens=True,
      return_tensors='pt',
      truncation=True,
      max_length=512
    )
    input_ids = tokens['input_ids']
    attention_mask = tokens['attention_mask']
  
  Why it works:
    - tokenizer() calls __call__() method
    - Returns same output dict as encode_plus
    - Compatible with transformers v5+
  
  File 2: src/refined/inference/standalone_md.py
  ────────────────────────────────────────────────
  
  Same replacement:
    OLD: self.tokenizer.encode_plus(...) 
    NEW: self.tokenizer(...)

Result: ✅ TOKENIZER FIXED
  - Text tokenization works
  - Mention detection can run
  - Preprocessing completes successfully

PROBLEM #3: PEM DATA FORMAT MISMATCH (INTERMITTENT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Error Encountered (Intermittent):
  TypeError: list indices must be integers, not str
  OR
  KeyError when accessing PEM dict
  
Root Cause:
  • PEM (Phrase-Entity-prior Map) stored in LMDB
  • Sometimes returns dict: {'entity_id': 5, 'score': 0.95}
  • Sometimes returns list: [5, 0.95]
  • Code expected only dict format
  • Different versions/datasets use different formats
  
File Affected:
  - src/refined/candidate_generation.py (entity candidate generation)
  
Impact: ⚠️ INTERMITTENT CRASHES
  - Works for some languages
  - Fails for others (e.g., Arabic)
  - Unpredictable behavior

Solution Implemented:

  File: src/refined/candidate_generation.py
  ─────────────────────────────────────────
  
  OLD CODE (Lines ~200-220):
    pem_data = self.pem.lookup(normalized_mention)
    entity_id = pem_data['entity_id']  # ❌ FAILS if pem_data is list
    entity_score = pem_data['score']
  
  NEW CODE (Fixed):
    pem_data = self.pem.lookup(normalized_mention)
    
    # Handle both dict and list formats
    if isinstance(pem_data, dict):
      entity_id = pem_data['entity_id']
      entity_score = pem_data['score']
    elif isinstance(pem_data, list) and len(pem_data) >= 2:
      entity_id = pem_data[0]
      entity_score = pem_data[1]
    else:
      # Fallback: no PEM data
      entity_id = None
      entity_score = 0.0
  
  Why it works:
    - Checks data type before accessing
    - Handles both production and fallback formats
    - Never crashes due to format mismatch

Result: ✅ PEM FORMAT ROBUST
  - All 9 languages process without crashes
  - Handles malformed/alternative PEM data
  - Evaluation continues smoothly

PROBLEM #6: OUTPUT BUFFERING / LOGGING INVISIBILITY (DEBUGGING)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Error Encountered:
  Evaluation runs for hours with zero output
  Can't tell if it's working or stuck
  Logs appear only at the very end (or never, if crash)
  
Root Cause:
  • Python buffers stdout by default (full buffering when piped)
  • Output not flushed until buffer full or process ends
  • Evaluation loop processes thousands of documents
  • Buffer never fills → output never appears
  
Impact: ⚠️ MONITORING IMPOSSIBLE
  - Can't see per-language progress
  - Can't detect hangs/crashes early
  - User thinks process is stuck
  - Debugging takes hours

Solution Implemented:

  Three-pronged approach:
  
  1. Environment Variable:
     export PYTHONUNBUFFERED=1
     
     Effect: Tells Python to use line buffering instead of full buffering
  
  2. Python Flag:
     python3 -u src/refined/evaluation/multilingual_e2e_evaluation_mewsli9.py ...
     
     Effect: Same as PYTHONUNBUFFERED=1, unbuffered I/O
  
  3. Code-Level:
     In multilingual_e2e_evaluation_mewsli9.py:
     
     print(f"[LANG {lang}] start: ...", flush=True)  # ← flush=True
     print(f"[LANG {lang}] done: recall={metrics.get_recall():.4f}", flush=True)
     
     Effect: Force flush after each print

  Complete Command:
    export PYTHONUNBUFFERED=1
    python3 -u src/refined/evaluation/multilingual_e2e_evaluation_mewsli9.py \
      ... (other args) ... 2>&1 | tee logs/mewsli9_final.log

Result: ✅ REAL-TIME VISIBILITY
  - Output appears immediately (line-buffered)
  - Progress visible as it happens:
    $ [LANG ar] start
    $ [LANG ar] done: recall=0.1234
    $ [LANG de] start
    $ ...
  - Logs captured AND displayed simultaneously (tee)

PART 3: HOW EVALUATION SCORES ARE COMPUTED
================================================================================

The evaluation script computes multiple metrics for each language:

1. **RECALL** (Entity Linking Recall @ 1)
   - What: % of mentions correctly linked to right entity
   - Calculation:
     Recall = (# correct predictions) / (# total mentions)
   - Range: 0.0 - 1.0 (or 0% - 100%)
   - Example: 0.1537 = 15.37% of mentions correctly linked
   - Result Line: "Recall: 0.1537"

2. **GOLD RECALL** (Mention Detection Recall)
   - What: % of mentions correctly detected/extracted
   - Calculation:
     Gold Recall = (# mentions detected) / (# annotated mentions)
   - Typically 70-90%
   - Shows that mention detection works (problem is disambiguation)
   - In MEWSLI-9 results: 83.60% for English, 90.62% for Arabic

3. **MD F1** (Mention Detection F1 Score)
   - What: Quality of mention boundary detection
   - Calculation: F1 = 2 × (Precision × Recall) / (Precision + Recall)
   - Range: 0.0 - 1.0
   - Example: 0.2661 = balanced score of mention finding+boundaries
   - Result Line: Shows as separate metric in summary

4. **F1 SCORE** (Entity Linking F1)
   - What: Harmonic mean of linking precision and recall
   - Calculation: F1 = 2 × (Precision × Recall) / (Precision + Recall)
   - Range: 0.0 - 1.0
   - In MEWSLI-9: 0.2320 for English (23.2%)
   - Lower F1 than recall means some false positives

5. **MACRO-AVG RECALL** (Average across all 9 languages)
   - What: Simple average of individual language recalls
   - Calculation: (recall_ar + recall_de + ... + recall_tr) / 9
   - Result: Average recall: 0.1537 (15.37%)
   - Interpretation: On average, 15.37% of mentions linked correctly

6. **MICRO-AVG F1** (Aggregate across all mentions)
   - What: F1 computed on all mentions combined
   - Calculation: 
     total_tp = sum of all true positives across all languages
     total_fp = sum of all false positives across all languages
     Micro F1 = 2 × (total_tp) / (2×total_tp + total_fp + total_fn)
   - Result: Micro-avg: 24.99 (%)
   - More representative than macro-avg for imbalanced languages

Code Location (evaluation.py):
  process_annotated_document() → Processes each document
  ├─ Run mention detection → Get spans
  ├─ Run entity disambiguation → Get entity IDs
  ├─ Compare with gold labels
  └─ Compute metrics (TP, FP, FN)
  
  evaluate_on_docs() → Aggregates across all documents
  ├─ Calls process_annotated_document() for each
  └─ Returns Metrics object with all statistics

Metrics Object Properties:
  metrics.get_recall() → Individual language recall
  metrics.get_summary() → Formatted output with all metrics
  metrics.tp → True positives count
  metrics.fp → False positives count
  metrics.fn → False negatives count

PART 4: EXPLAINING MEWSLI-9-SPECIFIC BEHAVIOR
================================================================================

Why Low F1 Despite High Gold Recall?

Gold Recall = Mention Detection Works ✅
  • 83.60% for English (detected 83.6% of mentions correctly)
  • 90.62% for Arabic (detected 90.6% of mentions)
  
F1 Score = Entity Disambiguation Fails ❌
  • 0.2320 for English (only 23.2% linked to RIGHT entity)
  • 0.0005 for Arabic (only 0.05% linked correctly!)

This means:
  ✅ Model FINDS the mentions (detection works)
  ❌ Model LINKS to WRONG entities (disambiguation fails)

Why does entity disambiguation fail?
  1. Non-Latin scripts: Model trained on English-heavy corpus
  2. Limited multilingual training data
  3. Wikidata entity descriptions may not be translated
  4. Ambiguous mentions without context

Conclusion: mReFinED strong at mention detection, weak at cross-lingual
entity disambiguation.
